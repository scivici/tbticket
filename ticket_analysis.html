Key Findings Summary

  1. External STIR/SHAKEN identity server pa2-call-identity-vm-1.netw.fr became unresponsive.
  2. Each incoming call triggered an HTTPS query via script.
  3. Because the HTTP layer used thread-per-request with no connection pooling, stalled requests accumulated rapidly.
  4. Concurrent requests rose from 0 to 439+ in about 4 minutes.
  5. This exhausted file descriptors (EMFILE errno 24), causing total HTTPS failure and cascading CMC errors.

Classification

HTTP/HTTPS module resource exhaustion during STIR/SHAKEN identity verification — external server unresponsiveness caused file descriptor exhaustion via thread-per-request HTTP architecture.

Root Cause Hypothesis

The external STIR/SHAKEN identity verification server became unresponsive around 16:05–16:07. The SBC created one thread and one new HTTP client per request, without connection reuse. As requests piled up, sockets and file descriptors were consumed until the process hit its limit and could no longer open new TCP connections.

Recommended Actions

  1. Verify availability and response times of pa2-call-identity-vm-1.netw.fr and pa3-call-identity-vm-1.netw.fr.
  2. Review the routing script HTTP timeout_ms value and reduce it to a reasonable range such as 2000–5000 ms.
  3. Lower max_http_query_pending_requests from 1000 to something safer such as 50–100.
  4. Increase process file descriptor limits, for example ulimit -n to 4096–8192.
  5. Raise a development ticket for HTTP connection pooling and circuit breaker behavior in CTBCAFHttpQueryMgr.
  6. Ask the customer whether the identity server had an outage or slowdown around March 5, 16:05–16:10.
  7. Check whether this is recurring, since the ticket mentions a volume of errors the same day.

Full Report

Summary

The ProSBC system experienced a cascading failure on 2026-03-05 between 16:05 and 16:14 UTC+1. The external STIR/SHAKEN identity verification server became unresponsive, causing HTTPS queries from the routing script to accumulate. Because the HTTP layer used a thread-per-request model with no connection pooling, ConcurrentRequests climbed from 0 to 439+ in about four minutes. This exhausted file descriptors and triggered widespread HTTPS, CMC, and verification failures.

Impact

All calls requiring STIR/SHAKEN verification were affected during the degradation window. Secondary effects included SIP RawSip pool exhaustion and CMC entity lookup failures.

Escalation Notes

This issue includes both an operational cause and a product architecture weakness. Support can mitigate it through timeouts, limits, and OS tuning, but the core design issue should still be escalated as a development improvement request.
